# Практика: кластер и запуск MPI

Теория из лекции 1 (SPMD, rank, коммуникатор, `MPI_Init`/`Finalize`) здесь проверяется руками: зайти на машину МФТИ, собрать программу, запустить несколько процессов и увидеть, что они — обычные процессы ОС, связанные общим **контекстом**.

## Подключение к машине МФТИ

Учётка: `mpi2026NN`, где `NN` — номер (у меня `13` -> `mpi202613`).

С кампуса / внутренней сети:

```bash
ssh mpi202613@head.vdi.mipt
# или по IP
ssh mpi202613@10.55.165.200
```

Снаружи — хост `remote` и отдельный порт:

```bash
ssh -p 52960 mpi202613@remote.vdi.mipt
```

`-p` — порт SSH. `head` — головная машина внутри, `remote` — вход с интернета.

## Сборка и запуск

Число процессов **статично**: программа его не меняет.

```bash
mpicc main.c                 # по умолчанию a.out
mpirun -np 5 ./a.out         # поднять 5 процессов
```

`-np` — *number of processes*. Без `mpirun` обычно получится один процесс (если вообще запустится).

`mpicc` — обёртка над обычным компилятором.

## Контекст (самое важное)

`mpirun -np 5` порождает **пять процессов ОС**. Они не «магически параллельны»: их объединяют в один **коммуникатор** — группа процессов + **контекст** общения.

Сообщения ходят только внутри своего контекста, чужие не подмешиваются. Поэтому можно иметь несколько коммуникаторов и не путать их трафик.

- все процессы данного запуска → `MPI_COMM_WORLD`
- внутри него у процесса уникальный **rank** `0 … N-1`
- rank — номер **в группе MPI**, не в операционной системе

Один и тот же процесс ОС может входить в несколько коммуникаторов и иметь в них разные rank. В ОС процесс при этом один.

`MPI_Init` процессы **не создаёт** — их уже поднял `mpirun`. Init только «связывает» их в коммуникатор.

## Процессы глазами ОС

MPI-процесс = обычный процесс Linux. Их можно увидеть через `ps`.

```bash
ps -A | grep a.out | wc -l
```

| кусок     | смысл |
| --------- | ----- |
| `ps`      | список процессов |
| `-A`      | *all*: все процессы системы, не только текущей сессии |
| `\|`      | pipe: stdout слева -> stdin справа |
| `grep a.out` | оставить строки, где есть `a.out` |
| `wc -l`   | посчитать строки (= сколько таких процессов) |

Пока `mpirun -np 5 ./a.out` ещё работает, `wc -l` должен показать около 5 (плюс иногда сам `mpirun`/`orted` — смотреть глазами, не только число).

`man mpi_get_processor_name` — manual-страница вызова (на кластере man по MPI обычно есть).

## Rank ≠ PID, узел ≠ rank

- **PID** — номер процесса в ОС (`ps`, `getpid()`). У каждого процесса свой, на разных машинах PID могут совпасть.
- **rank** — номер в коммуникаторе MPI. Его выдаёт `MPI_Comm_rank`. На нём строится логика (`if (rank == 0)`).
- **имя процессора/узла** — на какой машине крутится процесс. Несколько rank могут жить на одном узле.

```c
int MPI_Get_processor_name(char *name, int *resultlen);
```

`name` — буфер не короче `MPI_MAX_PROCESSOR_NAME`. `resultlen` — фактическая длина строки (без `'\0'`).

### Пример

```c
#include <stdio.h>
#include <mpi.h>

int main(int argc, char *argv[])
{
    int rank, size, namelen;
    char name[MPI_MAX_PROCESSOR_NAME];

    MPI_Init(&argc, &argv);
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);
    MPI_Get_processor_name(name, &namelen);

    printf("rank %d of %d, pid %d, node %s\n",
           rank, size, (int)getpid(), name);

    MPI_Finalize();
    return 0;
}
```

Порядок строк не гарантирован. На одном узле `node` совпадёт у всех, `pid` и `rank` — нет.

## Кратко

1. Зайти: `head` внутри, `remote -p 52960` снаружи.
2. Собрать `mpicc`, запустить `mpirun -np N`.
3. `N` процессов ОС склеиваются в `MPI_COMM_WORLD` с общим контекстом.
4. rank — логический номер в этой группе; PID — номер в ОС.
5. `ps -A | grep …` показывает, что MPI-процессы — настоящие процессы.
6. `MPI_Get_processor_name` говорит, на каком узле сидит rank.
